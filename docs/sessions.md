# Steam Wishlist Sorter — промпты по сессиям (версия для публикации на GitHub)

Проект идёт в портфолио, поэтому git ведётся с первого коммита, а не приклеивается в конце.
История коммитов — часть того, что будут смотреть.

## Правила работы с git на весь проект

- **Версионированием управляешь ты вручную в Fork.** Claude Code не выполняет git-команды:
  ветки, коммиты и пуши делаешь сам. Это запрещено ему в `CLAUDE.md` (см. Сессию 0),
  а в конце каждой сессии он предлагает готовые сообщения коммитов, которые ты применяешь в Fork.
- Одна сессия = одна ветка = один Pull Request в `main`. Даже в соло-проекте это выглядит
  профессионально и даёт удобную точку отката.
- Ветки: `feat/core-ranking`, `feat/ui-categorize`, `feat/results-export`, `feat/userscripts`.
  Создавай ветку в Fork **до** запуска сессии.
- Коммиты в формате Conventional Commits со scope: `feat(ranking):`, `fix(ui):`, `test(storage):`,
  `docs(readme):`, `chore(ci):`, `refactor(import):`.
- Допустимые scope: `ranking`, `import`, `storage`, `ui`, `results`, `export`, `userscripts`,
  `ci`, `docs`, `git`, `repo`.
- Сообщения коммитов и PR — на английском. Это стандарт для публичного репозитория, даже когда
  README и интерфейс на русском.
- `main` всегда в рабочем состоянии: тесты зелёные, приложение открывается.

## Сессия 1 — Ядро: модель данных, хранилище, алгоритм сортировки + тесты

> Продолжаем проект. Прочитай `CLAUDE.md` — правила оттуда действуют, в том числе запрет
> на выполнение git-команд. Ветку `feat/core-ranking` я уже создал сам, переключаться не нужно.
> Это первая содержательная сессия из четырёх. **UI в этой сессии не делаем вообще.**
>
> Задача: собрать ядро проекта — чистый JS без фреймворков, ES-модули, и покрыть логику тестами.
>
> **Стек и структура**
> - Vanilla JS (ES modules), без сборщика. Тесты — Vitest или node:test, на твой выбор, обоснуй.
> - Разложи по модулям в `src/`: `model.js`, `import.js`, `storage.js`, `ranking.js`.
> - `package.json` только для тестов; само приложение должно работать без npm.
>
> **Модель позиции**
> `{ appId, title, url, imageUrl, wishlistPosition, kind: 'game' | 'dlc' | 'unknown' }`.
> Идентификатор — `appId`. Дубликаты по `appId` при повторном импорте не создаются,
> данные существующей позиции обновляются, а назначенная категория и результаты сравнений сохраняются.
>
> **Импорт и нормализация (`import.js`)**
> Функция принимает произвольный JSON и приводит его к модели. Поддержи несколько форматов входа:
> массив объектов, объект вида `{ "appid": {...} }` (старый формат Steam), наш собственный формат экспорта.
> Невалидные записи не роняют импорт, а собираются в отчёт: сколько добавлено, обновлено, пропущено и почему.
>
> **Категории**
> Шесть уровней: `must` (Очень хочу), `want` (Хочу), `maybe` (Возможно), `unlikely` (Маловероятно),
> `meh` (Почти не интересует), `remove` (Удалить из желаемого).
> В итоговом списке любая позиция из более высокой категории всегда выше любой позиции из более низкой.
> `remove` в сортировке не участвует.
>
> **Алгоритм ранжирования (`ranking.js`) — главная часть сессии**
> Сортировка идёт независимо внутри каждой категории. Требования:
> - Адаптивный comparison sort (merge sort или аналог), а не случайные пары.
> - Состояние алгоритма полностью сериализуемо в JSON и восстанавливается без потерь:
>   в любой момент можно сохранить, «перезагрузиться» и продолжить ровно с той же пары.
> - Транзитивность: если известно A > B и B > C, пара A/C не задаётся.
> - Ответ «примерно одинаково» создаёт группу равного приоритета; порядок внутри группы стабильный.
> - Ответ «не могу решить» откладывает пару и возвращает её позже, но не зацикливает алгоритм.
> - Отмена последнего ответа откатывает и сравнение, и состояние алгоритма.
> - Удаление позиции прямо во время сортировки не ломает текущее состояние.
> - API вида: `getNextPair()`, `submitAnswer(...)`, `undo()`, `getProgress()`, `getResult()`,
>   `serialize()`, `deserialize()`. Прогресс отдаёт выполненные сравнения, оценку оставшихся и процент.
> - Публичные функции снабди JSDoc-комментариями на английском: это публичный репозиторий.
>
> **Хранилище (`storage.js`)**
> Обёртка над localStorage (с запасом на переезд в IndexedDB): сохранение всего состояния после
> каждого действия, экспорт состояния в JSON, импорт состояния, создание новой сессии.
> Модуль не должен зависеть от DOM — в тестах подменяется заглушкой.
>
> **Тесты — обязательны, и они должны проходить**
> Покрой минимум: 0, 1, 2, 3 и 200 позиций; дубликаты appId при повторном импорте; позиции без
> imageUrl; ничья; серия ничьих подряд; отложенная пара; отмена последнего ответа; отмена нескольких
> подряд; сохранение и восстановление состояния посреди сортировки; транзитивность (проверь, что число
> сравнений заметно меньше, чем n²); удаление позиции в процессе; корректность итогового порядка
> относительно категорий.
> Добавь тест-«обезьяну»: 200 позиций, случайный, но согласованный оракул предпочтений — алгоритм
> должен сойтись за разумное число сравнений и выдать порядок, совпадающий с оракулом.
>
> **CI**
> Добавь `.github/workflows/test.yml`: GitHub Actions, запуск тестов на push и pull request,
> Node LTS, минимальная конфигурация без лишних шагов.
>
> **В конце сессии**
> Запусти тесты, покажи вывод, исправь падения. Кратко опиши, какой алгоритм выбрал и почему,
> и какое API у `ranking.js` — во второй сессии я буду строить UI поверх него.
> Git-команды не выполняй. Вместо этого предложи разбивку на несколько осмысленных коммитов:
> для каждого — сообщение в формате Conventional Commits со scope и список входящих в него файлов.

## Сессия 2 — Интерфейс: импорт, категоризация, попарные сравнения

> Продолжаем проект. Прочитай `CLAUDE.md` и существующий код в `src/`, не меняй публичное API
> `ranking.js`. Ветку `feat/ui-categorize` я создал сам, git-команды не выполняй.
> В этой сессии делаем интерфейс: экран импорта, этап категоризации и этап попарных сравнений.
>
> **Общее**
> - `index.html` + `styles.css` + модули UI. Тёмная тема, визуально родственная Steam, но не копия.
> - Экран 1920×1080 и адаптив до узкого окна. Без горизонтальной прокрутки.
> - Заметные состояния hover и focus, полная доступность с клавиатуры.
> - `start.bat` для Windows, поднимающий локальный HTTP-сервер (ES-модули не работают через `file://`).
>   Учти, что Python может отсутствовать — предусмотри запасной вариант и напиши об этом.
> - После каждого действия состояние автоматически сохраняется через `storage.js`.
>
> **Экран импорта**
> Три способа: загрузка JSON-файла, вставка JSON в textarea, импорт сохранённого состояния приложения.
> Показывай отчёт импорта (добавлено / обновлено / пропущено). Понятные сообщения об ошибках вместо
> тишины или технических исключений.
>
> **Этап 1 — категоризация**
> Одна позиция на экране: крупная обложка, название, тип (игра / DLC), ссылка «Открыть в Steam»
> (открывается в новой вкладке), прогресс вида `37 из 204`.
> Шесть кнопок категорий + горячие клавиши `1`–`6`. Также: вернуться к предыдущей позиции (`←`),
> отложить позицию, пропустить весь этап и сразу перейти к сравнениям, изменить выбор позже.
> Позиции без обложки показывают аккуратный плейсхолдер, а не битую картинку.
>
> **Этап 2 — попарные сравнения**
> Две позиции рядом: обложки одинакового размера, названия, тип, ссылки на Steam.
> Ответы: левая, правая, примерно одинаково, не могу решить (отложить), «одну из позиций больше не хочу»,
> отменить последний ответ.
> Горячие клавиши: `A` / `←` — левая, `D` / `→` — правая, `S` / `↓` — одинаково, `Space` — отложить,
> `Backspace` — отменить.
> Шапка показывает: текущую категорию, число сделанных сравнений, примерную оценку оставшихся,
> общий процент и кнопку паузы.
> Всю логику бери из `ranking.js`, ничего не дублируй в UI.
>
> **В конце сессии**
> Подними сервер, создай тестовый набор из 20 фиктивных позиций (две из них — без обложки, одна DLC),
> пройди оба этапа, перезагрузи страницу посреди сортировки и убедись, что она продолжается с того же
> места. Проверь консоль браузера — ошибок быть не должно. Исправь найденное.
> Тестовый набор фиктивных позиций сохрани в репозиторий как `tests/fixtures/sample-wishlist.json` —
> он пригодится и для демонстрации, и для будущих тестов.
> Git-команды не выполняй; предложи разбивку на коммиты текстом.

## Сессия 3 — Итоговый экран и экспорты

> Продолжаем. Прочитай `CLAUDE.md` и существующий код. Ветку `feat/results-export` я создал сам,

>
> **Итоговый список**
> Сквозная нумерация. Для каждой позиции: номер, название, категория, тип, ссылка на Steam, App ID.
> Возможности: drag-and-drop для ручного перетаскивания, смена категории прямо в списке, поиск по названию,

> **Опасные действия**

> экспорт состояния → новая сессия → импорт состояния обратно. Убедись, что всё восстановилось,

## Сессия 4 — Userscripts, README и публикация

> Финальная сессия. Прочитай `CLAUDE.md`. Ветку `feat/userscripts` я создал сам, git-команды
> не выполняй. Два Tampermonkey-скрипта и подготовка репозитория к публикации: проект идёт
> ко мне в портфолио, README будут читать посторонние люди.
>
> **`userscripts/steam-wishlist-export.user.js`**
> Работает на странице моего Steam Wishlist. Собирает все позиции с учётом пагинации и ленивой
> подгрузки — не предполагай, что все 200 позиций сразу в DOM: прокручивай и дожидайся подгрузки,
> с ограничением по времени и защитой от бесконечного цикла.
> Для каждой позиции: App ID, название, ссылка, URL обложки, текущая позиция в wishlist, тип
> (игра / DLC / unknown, если определить нельзя).
> Экспорт в JSON-файл в формате, который понимает наше приложение.
> Никаких cookie, токенов и любых секретов. Никаких запросов на сторонние адреса.
> Все селекторы Steam вынеси в один объект-адаптер в начале файла, с комментариями, чтобы их можно
> было обновить, когда Steam изменит вёрстку. Если селекторы не сработали — скрипт показывает понятное
> сообщение и останавливается, а не отдаёт пустой или частичный результат молча.
>
> **`userscripts/steam-wishlist-import-order.user.js`**
> Работает только на страницах Steam Wishlist. Позволяет загрузить наш итоговый JSON и сопоставляет
> позиции по App ID (название — только для отображения, не для сопоставления).
> Сначала показывает отчёт: сколько позиций найдено на странице, сколько не найдено, есть ли дубликаты,
> какой порядок будет применён. Никаких изменений до явного подтверждения.
> Дальше — важное ограничение: **сначала изучи, как сейчас реально устроено ручное упорядочивание
> wishlist в интерфейсе Steam.** Если надёжного штатного механизма нет, не имитируй рабочее решение.
> Тогда оставь скрипт в безопасном режиме предпросмотра: отчёт, подсветка позиций и понятная инструкция
> по ручному переносу. Честно напиши в README, что именно не автоматизировано и почему.
