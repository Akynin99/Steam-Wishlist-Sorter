# CLAUDE.md — контекст проекта Steam Wishlist Sorter

Этот файл читается в начале каждой сессии. Правила отсюда действуют всегда,
даже если в промпте сессии они не повторены.

## О проекте

Steam Wishlist Sorter — локальное веб-приложение для ранжирования списка желаемого
в Steam. Пользователь импортирует свой wishlist, раскладывает позиции по категориям,
затем упорядочивает их внутри категорий попарными сравнениями и получает итоговый
пронумерованный список с экспортом в JSON, CSV и текст.

Цель — инструмент, которым реально пользуются с wishlist на 200+ позиций, а не
демонстрация алгоритма. Проект публичный, идёт в портфолио: код, комментарии,
история коммитов и README читают посторонние люди.

## Стек

- Vanilla JS, ES-модули. Без фреймворков, без сборщика, без транспиляции.
- HTML + CSS без препроцессоров. Тёмная тема, родственная Steam, но не копия.
- Node нужен только для тестов и для локального сервера (`server.js`, чистый Node
  без зависимостей). ES-модули не работают через `file://`, поэтому приложение
  открывается с локального HTTP-сервера. Этот же сервер отвечает на `/api/*`:
  прямой импорт из аккаунта Steam делается им, потому что браузеру CORS не даёт.
- Минимальная версия Node — 20. Разработка ведётся на 24 LTS. В CI указывается та же
  мажорная версия, чтобы локальный прогон и GitHub Actions не расходились.
- Линтеров, форматтеров и CI-инструментов сверх GitHub Actions не добавляем.

## Тесты

- Только встроенные `node:test` и `node:assert`. Ничего больше.
- **Сторонних зависимостей у проекта нет и не должно появиться.** `node_modules`
  не создаётся, `npm install` не запускается, `npx <пакет>` не предлагается —
  это тянет пакеты из сети и противоречит духу локального приватного приложения.
- `package.json` существует по сути ради одного скрипта: `"test": "node --test"`.
- Запуск: `node --test`.

## Язык интерфейса

- Все тексты интерфейса живут в словарях `src/i18n.js` — плоские ключи, значения строки,
  подстановка параметров вида `{count}`. Ни одной строки интерфейса в разметке и в модулях
  экранов: разметка ссылается на ключ через `data-i18n`, код зовёт `t(key, params)`.
- **Английский — язык по умолчанию всегда.** `navigator.language` не спрашивается: демо
  открывается на английском у любого посетителя. Выбор хранится в `settings.language`,
  рядом с тумблером обложек, и переживает перезагрузку.
- Наборы ключей всех словарей совпадают в точности. Это проверяет тест в `tests/i18n.test.js`,
  и это главный тест модуля: он ловит забытый перевод. Тест ходит по `LANGUAGES`, поэтому новый
  язык попадает под него сам.
- **Новый язык — четыре правки и ни одного нового механизма:** блок словаря и код в
  `DICTIONARIES`, строка правила в `PLURAL_RULES` (по CLDR), запись в `CSV_SEPARATORS`
  в `export.js`, код в `LANGUAGES` с самоназванием в `LANGUAGE_NAMES` и `<option>` в разметке.
  Если механику приходится трогать где-то ещё — это ошибка механики, а не языка.
- Считаемые фразы задаются тремя формами `.one` / `.few` / `.many` во всех языках
  и берутся через `plural(key, count)`. Языку, которому хватает двух, `few` объявляется равной
  `many`: наборы ключей от этого не расходятся.
- Подписи категорий — в словарях, а не в модели: `CATEGORIES` в `model.js` несёт только
  `id` и `sortable`, а `categoryLabel()` отдаёт текст текущего языка.
- Смена языка — перерисовка, а не перезапуск: ни один ответ и ни одна позиция в сортировке
  не теряются, `document.documentElement.lang` меняется вместе с языком.
- Экспорты следуют за языком: заголовки CSV, подписи категорий и типов, а также разделитель
  CSV — запятая для `en` по RFC 4180, точка с запятой для остальных. Правило не про русский,
  а про десятичный разделитель: где он запятая, там Excel режет файл по точке с запятой.
  Идентификаторы (`category`, `kind`, `origin`) от языка не зависят никогда.
- **Переводы, кроме `en` и `ru`, не вычитаны носителями, и README говорит это вслух.** Убирать
  этот абзац нельзя: молчаливое притворство, что перевод профессиональный, хуже оговорки.
- `server.js`, `start.bat` и оба userscript-а — только английские, без вариантов. Букмарклет —
  исключение: его тексты берутся из словарей и говорят на языке, который был выбран в момент
  сборки ссылки.

## Две темы и токены

- Тем ровно две: `modern` — та, что была всегда, и `steam` — синевато-серое настроение магазина,
  собранное из собственных значений. Ни логотипа, ни картинок магазина, ни одного внешнего файла.
- Тема — это только `data-theme` на корневом элементе. Разметка одна, ни один экран не
  пересобирается, и никакой класс никуда не добавляется.
- **Всё, что тема может захотеть поменять, живёт кастомными свойствами в `:root`**, а
  `[data-theme="steam"]` переопределяет только то, с чем не согласен. Отличия не сводятся к цвету:
  скругления, рамки, плотность, регистр и вес заголовков тоже в токенах.
- **Ниже блока токенов сырых цветов быть не должно.** Сырой цвет — это место, где вторая тема
  останется бирюзовой. Это, а также «вторая тема не изобретает токенов, которых нет у первой» и
  «каждый использованный токен объявлен», закрыто тестом `tests/styles.test.js`, который читает
  `styles.css` как текст. Удалять его нельзя: правило ломается молча, CSS об этом не сообщает.
- Тема хранится в `settings.theme` рядом с языком и обложками. Неизвестное значение и файл
  состояния, сохранённый до появления второй темы, читаются как `modern` — это `theme.js`.
- **Тема ставится до первой отрисовки, блокирующим инлайн-скриптом в `<head>`.** Модули
  запускаются поздно, и на холодном кэше страница до полусекунды стояла бы в чужой теме.
  Скрипт читает одно слово из отдельного ключа `steam-wishlist-sorter/theme` — зеркала темы,
  которое `applyTheme()` пишет рядом с ключами `screen` и onboarding. Ровно `steam` включает
  тему магазина, всё остальное — отсутствие ключа, запрещённое хранилище, мусор, значение из
  ещё не написанной версии — оставляет атрибут не выставленным, то есть `modern`.
- **Скрипт в голове не знает формата состояния и знать не должен.** Он не разбирает JSON и не
  ходит в `settings`: иначе следующее изменение формата сломало бы его молча, а видно это
  только как чужая тема на полсекунды. Источник истины остаётся в `settings.theme`, зеркало —
  копия одного слова. Обе половины держит `tests/theme.test.js`: он вынимает скрипт из
  `index.html` и исполняет его, поэтому ключ нельзя переименовать с одной стороны, а правило
  чтения не может разойтись с `normalizeTheme()`. Удалять его нельзя.
- Язык по-прежнему применяется при инициализации модуля: разметка несёт английские строки,
  поэтому до модулей страница читается правильно, и мигания нет. Это известно и принято.

## Доступность

Проверяется целиком, а не декларируется. Все пункты ниже — инварианты: их ломает любая правка,
которая про них не знает.

- **Контраст обычного текста — не ниже 4.5 в обеих темах.** Самый тихий из трёх уровней текста,
  `--text-dim`, выставлен ровно так, чтобы проходить на самой светлой поверхности, на которой он
  встречается. Понижать его или гасить текст `opacity` нельзя: погашенный текст уходит под порог.
- **Цвет — никогда не единственный носитель смысла.** Состояние строки результата несёт текстовую
  метку и стиль рамки, выбранная категория — галочку, выбранный фильтр — подчёркивание и жирность,
  пройденный этап — галочку вместо номера и скрытый текст состояния.
- **Горячие клавиши молчат в полях ввода, при открытом меню и при открытом диалоге.** Это
  `isHotkeyBlocked()` в `ui-common.js`, и он смотрит на любой открытый `dialog`, а не на список.
- **У перетаскивания строки результата есть клавиатурная замена:** стрелки ходят по списку,
  <kbd>Ctrl</kbd> + стрелка переставляет строку. На весь список ровно один tab-stop, и элементы
  внутри строк следуют за ним — иначе двести строк станут двумястами остановками табуляции.
- **Диалоги — на `<dialog>`.** Ловушка фокуса и Escape достаются от браузера; фокус возвращается на
  элемент, который диалог открыл. Обучающие панели для этого фокусируют заголовок этапа *до*
  `showModal()`.
- **Полоски прогресса несут `role="progressbar"` и `aria-valuenow`.** Значение ставится вместе с
  шириной, одним вызовом `setProgress()`: написанные порознь, они разъезжаются.
- **Горизонтальной прокрутки нет ни на одной ширине.** Проверено от 280 px до 1920 px, в обоих
  языках и обеих темах.

## Приватность

Пользовательские данные никогда не покидают браузер и никуда не отправляются.
Внешних запросов за всё время работы приложения ровно два вида, и оба называются вслух:

- загрузка обложек игр с CDN Steam по публичному URL — отключается тумблером в настройках;
- импорт прямо из аккаунта: по нажатию кнопки `server.js` спрашивает у Steam список
  желаемого названного аккаунта. Запрос уходит только в Steam, только по прямой просьбе
  пользователя, и ответ возвращается в браузер, а дальше никуда не идёт.

Userscript-ы и букмарклет — отдельная история, и их надо называть отдельно: скрипт экспорта
не делает ни одного сетевого запроса, а скрипт переноса порядка и букмарклет делают ровно один —
`POST` записи на тот же origin Steam, со страницы которого они запущены, и только после
подтверждения. Секрета в этом запросе нет и не нужно: ни `sessionid`, ни токена в теле, право
на запись подтверждает кука, которую браузер прикладывает сам, потому что адрес того же
происхождения. Куки они не читают и в тело кладут только App ID и их места.

Букмарклет собирается нашей страницей, но выполняется на странице Steam. В адрес ссылки уходят
только код, App ID и тексты интерфейса выбранного языка: ни названий, ни ссылок на магазин,
ни адреса локального сервера, ни токенов. App ID публичны. Это закрыто тестами в
`tests/bookmarklet.test.js`, и проверку «в ссылке нет ничего, кроме кода и чисел» удалять нельзя.

Формулировки вида «никаких внешних запросов» без этих оговорок неверны и не должны
появляться ни в README, ни в интерфейсе, ни в комментариях. Точные формулировки выше —
единственные допустимые.

## Запись порядка обратно в Steam

Записей две, и запрос у них один и тот же: букмарклет (`src/bookmarklet.js`) — основной путь,
userscript (`userscripts/steam-wishlist-import-order.user.js`) — расширенный, с бэкапом и сверкой.
Всё сказанное ниже относится к обоим. Букмарклет страницу Steam не читает: порядок уже вшит
в адрес ссылки, поэтому ни селекторов строк, ни прокрутки, ни проверки полноты чтения в нём нет
и появляться не должно — в этом и смысл, ломаться там нечему.

Механизм перехвачен из живого перетаскивания строки и проверен на реальном списке. Адрес
один на всех, аккаунт в нём не участвует:

```
POST https://store.steampowered.com/wishlist/action
Content-Type: application/json; charset=utf-8
X-Valve-Request-Type: mutationAction
{ "m": "Reorder", "mp": [ [ { "appid": 1509510, "priority": 1 }, … ] ] }
Ответ: { "data": { "result": 1 } }
```

- `mp` — массив, внутри которого **один** элемент, и уже он список пар. Двойные скобки не опечатка.
- `X-Valve-Request-Type: mutationAction` обязателен. Без него тот же самый запрос — тот же адрес,
  метод и тело — отвечает `400` с пустым телом, и причина в ответе не названа ничем. Заголовок и есть
  защита от подделки запроса с чужого сайта: чужая страница может заставить браузер отправить POST
  с твоей кукой, но своего заголовка на него не поставит. Убирать эту строку нельзя, и её отсутствие
  роняет тесты в `tests/reorder-userscript.test.js` и `tests/bookmarklet.test.js`.
- Успех — только `data.result === 1`. Поле `success` относилось к прежнему эндпоинту
  `/wishlist/profiles/<id>/reorder/` с `sessionid`; тот путь нынешняя страница не использует,
  `g_sessionID` на неё не кладётся, и возвращать его нельзя.
- `priority` — сквозная нумерация расставленных вручную позиций с единицы; нерасставленные
  лежат в конце с нулём. Список отправляется целиком, приоритетами от 1 до N, — но не потому, что
  Steam якобы растасовывает частичный список: настоящее перетаскивание шлёт две пары, и они
  применяются как есть. Целиком — чтобы порядок был задан однозначно и не зависел от того, что Steam
  делает с позициями, о которых его не спросили. Этого никто не измерял, и wishlist — плохое место
  для проверки. Формулировок про «раскидывает» и «растасовывает» в проекте быть не должно.
- Отсюда необратимое следствие, которое обязано быть названо словами в панели перед
  подтверждением и в README: после записи приоритет получают **все** позиции, включая те,
  у которых его не было. Бэкап вернёт порядок, но не вернёт состояние «без приоритета».
- SteamID для записи не нужен. Аккаунт определяется только как справка в отчёте — чтобы
  пользователь заметил, что открыт чужой список: запись уходит в список того, под кем вошёл
  браузер, а App ID читаются с открытой страницы. Неизвестный аккаунт и страница, называющая
  два аккаунта, запись не блокируют. Единственный оставшийся отказ — числовой адрес одного
  аккаунта при `g_steamID` другого.

## Прямой импорт из Steam — правила прокси

`/api/steam/*` принимает идентификатор аккаунта или список App ID и **никогда не URL**:
локальный сервер, пересылающий произвольные адреса, — это открытый прокси, через который
страница в браузере ходит в домашнюю сеть хозяина.

- Разрешённые хосты — закрытый список `ALLOWED_HOSTS` в `steam.js`: `api.steampowered.com`,
  `store.steampowered.com`, `steamcommunity.com`. Всё остальное отвергается в
  `assertAllowedUrl()`, через который проходит каждый запрос и каждый редирект.
- Адреса собираются в коде из уже проверенных значений: SteamID64 — 17 цифр, ник — набор
  символов Steam. Пользовательский ввод в адрес не склеивается никогда.
- API отвечает только на запросы, адресованные `localhost`: страница с любого сайта может
  постучаться на локальный порт, и имя, которое резолвится в 127.0.0.1, — это DNS rebinding.
- Всё перечисленное закрыто тестами. Тест, который поднимает сервер-ловушку и убеждается,
  что его так и не позвали, удалять нельзя: он и есть доказательство, что прокси закрыт.
- Сторонние CORS-прокси не предлагать ни при каких обстоятельствах: они отправили бы
  wishlist на чужой сервер, что прямо противоречит разделу «Приватность».

## Результат доступен в любой момент

Сортировка длинная: 200 позиций — это порядка тысячи сравнений, и реальный пользователь
бросит её на середине. Поэтому незавершённое состояние обязано давать осмысленный
итоговый список: всё, что уже выводится из графа предпочтений, упорядочивается
топологически, а позиции с ещё не определённым порядком получают стабильный запасной
порядок по `wishlistPosition`. Итоговый экран честно показывает, какая часть списка
упорядочена сравнениями, а какая стоит в запасном порядке.

`getResult()` обязан работать на любом состоянии, включая пустое и незавершённое.
Инструмент, который до самого конца не отдаёт ничего, бесполезен.

## Ручной порядок — отдельный слой

Ответ на сравнение и перетаскивание строки — разные по природе утверждения, и они хранятся
раздельно. Ответ говорит о паре и идёт в граф, который append-only и обязан быть без
противоречий. Перетаскивание говорит о списке и вполне может противоречить ответу,
данному раньше.

Поэтому ручной ход хранится как `{ appId, anchor, side }` — «эта позиция идёт сразу за той» —
и ходы переигрываются поверх порядка, который дали сравнения. Следствия: новые ответы
продолжают улучшать список, а расстановка накладывается сверху и не затирается; ход,
у которого якорь ушёл в другую категорию, не теряется, а перестаёт применяться, пока якорь
не вернётся; где ход спорит со сравнениями, побеждает ход, но строка помечается
`entry.manual` и не считается подтверждённой.
